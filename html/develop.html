Wireshark Cheat Sheet

Wireshark Capture Filters Overview

Capture Filter is Not a Display Filter

Capture filters (like tcp port 80) are not to be confused with display filters (like tcp.port == 80).

  • Capture Filters: Much more limited and are used to reduce the size of a raw packet capture. They are set before starting a packet capture and cannot be modified during the capture.
  • Display Filters: Used to hide some packets from the packet list. They do not have this limitation and you can change them on the fly.

Interface Locations:

  • In the main window, one can find the capture filter just above the interfaces list and in the interfaces dialog.
  • The display filter can be changed above the packet list.

Capture Filter Examples

Capture only traffic to or from IP address 172.18.5.4:

host 172.18.5.4

Capture traffic to or from a range of IP addresses:

net 192.168.0.0/24

or

net 192.168.0.0 mask 255.255.255.0

Capture traffic from a range of IP addresses (Source Only):

src net 192.168.0.0/24

or

src net 192.168.0.0 mask 255.255.255.0

Capture traffic to a range of IP addresses (Destination Only):

dst net 192.168.0.0/24

or

dst net 192.168.0.0 mask 255.255.255.0

Capture only DNS (port 53) traffic:

port 53

Capture non-HTTP and non-SMTP traffic on your server (Equivalent syntaxes):

host www.example.com and not (port 80 or port 25)
host www.example.com and not port 80 and not port 25

Capture except all ARP and DNS traffic:

port not 53 and not arp

Capture traffic within a range of ports:

(tcp[0:2] > 1500 and tcp[0:2] < 1550) or (tcp[2:2] > 1500 and tcp[2:2] < 1550)

With newer versions of libpcap (0.9.1 and later):

tcp portrange 1501-1549

Capture only Ethernet type EAPOL:

ether proto 0x888e

Reject ethernet frames towards the Link Layer Discovery Protocol Multicast group:

not ether dst 01:80:c2:00:00:0e

Capture only IPv4 traffic (Shortest filter to discard lower layer protocols like ARP and STP):

ip

Capture only unicast traffic (Useful to clean out background noise like broadcast/multicast announcements):

not broadcast and not multicast

Capture IPv6 "all nodes" (router and neighbor advertisement) traffic (Can be used to find rogue RAs):

dst host ff02::1

Capture HTTP GET requests:

Looks for the bytes 'G', 'E', 'T', and ' ' (hex values 47, 45, 54, and 20) just after the TCP header. The snippet ((tcp[12:1] & 0xf0) >> 2) calculates the variable TCP header length.

port 80 and tcp [((tcp [12:1] & 0xf0) >> 2):4] = 0x47455420

Useful Filters (Worms & Exploits)

Blaster and Welchia are RPC worms.

Blaster Worm:

dst port 135 and tcp port 135

Welchia Worm:

This filter isolates an ICMP echo request that is exactly 92 bytes long and holds an ICMP payload beginning with 4 bytes of hex A's. This acts as the signature of the welchia worm right before it attempts a system compromise.

ip[2:2] == 48
icmp [icmptype] == icmp-echo and ip[2:2] == 92 and icmp [8:4] == 0xAAAAAAAA

General Worm Scanning (Ports 135, 445, 1433):

Many worms contact hosts on ports 135, 445, or 1433. This targeted filter acts independently of a specific worm variant by capturing SYN packets originating exclusively from a local network towards those ports. (Note: Modify the network filter subnet block to match your local architecture).

dst port 135 or dst port 445 or dst port 1433 and tcp[tcpflags & (tcp-syn) != 0 and tcp[tcpflags & (tcp-ack) == 0 and src net 192.168.0.0/24

Heartbleed Exploit:

tcp src port 443 and (tcp[(tcp[12] & 0xF0) > 4) * 4] == 0x18) and (tcp[((tcp[12] & 0xF0) >> 4) * 4 + 1] == 0x03) and (tcp [((tcp[12] & 0xF0) >> 4) * 4 + 2] < 0x04) and ((ip[2:2] - 4 * (ip[0] & 0x0F) - 4 * ((tcp [12] & 0xF0) >> 4) > (69))

Default Capture Filters (Remote Session Mitigation)

Wireshark dynamically detects if it is running over a remote connection (such as SSH or Remote Desktop). If detected, it applies an automated internal default capture filter to omit administrative session overhead traffic. Environment variables are checked sequentially in this order:

1. SSH_CONNECTION not (tcp port srcport and addr_family host srchost and tcp port dstport and addr_family host dsthost)
2. SSH_CLIENT not (tcp port srcport and addr_family host srchost and tcp port dstport)
3. REMOTEHOST not addr_family host host
4. DISPLAY not addr_family host host
5. CLIENTNAME (RDP) not tcp port 3389

Note: addr_family resolves to either "ip" or "ip6".

Discussion Notes & Queries

Blaster Alternative Parameter Verification:

Symantec documentation indicates Blaster probes 135/tcp, 4444/tcp, and 69/udp. Would the following filter configuration prove more reliable?

(tcp dst port 135 or tcp dst port 4444 or udp dst port 69) and ip[2:2] == 48

— Gerald Combs

Q: What is a good filter for just capturing SIP and RTP packets?

A: On most standard deployments utilizing port 5060, apply these variations depending on protocol constraint:

  • tcp port sip — Capture only SIP TCP infrastructure frames
  • udp port sip — Capture only SIP UDP layer frames
  • port sip — Capture both TCP and UDP records on port 5060

Note: If these definitions prompt a "parse error", change the string token keyword sip directly to the integer 5060. For non-standard ports, supply the literal port digit parameter.

Capturing Dynamically Assigned RTP Streams:

Because RTP addresses spin up dynamically, constrain your structural rules to enforce UDP parameters, even sequence matching properties, strict version syntax validation checks, and low overall packet sizes:

udp[1] & 1 != 1 && udp [3] & 1 != 1 && udp [8] & 0x80 == 0x80 && length < 250

This strategy captures occasional non-RTP fragments matching structural configurations (such as random DNS queries), but reliably isolates complete enterprise voice environment contexts.

Specialized Link-Layer Capture Filters

Capture WLAN traffic without Beacons:

link[0] != 0x80

Capture all traffic originating (source) in the IP range 192.168.XXX.XXX:

src net 192.168

Capture PPPoE traffic (Standalone or combined conditional logic structures):

pppoes
pppoes and (host 192.168.0.0 and port 80)

Capture VLAN traffic (Standalone or combined conditional logic structures):

vlan
vlan and (host 192.168.0.0 and port 80)

Wireshark Display Filters Overview

Reminder: Display filters are completely distinct from capture filters.

Show only SMTP (port 25) and ICMP traffic:

tcp.port eq 25 or icmp

Show only localized LAN traffic (192.168.x.x) exclusively between internal hosts (Drops internet routes):

ip.src==192.168.0.0/16 and ip.dst ==192.168.0.0/16

TCP Buffer Full Alert (Source signaling to destination host to pause immediate data transmission):

tcp.window_size == 0 && tcp.flags.reset != 1

Filter Core Windows Exchange Infrastructure Traffic (Drops noisy environmental variables):

smb || nbns || dcerpc || nbss || dns

Sasser Worm Operational Footprint Identification:

ls_ads.opnum == 0x09

Isolate explicit raw 3-byte hexadecimal sequences anywhere at the front of the UDP payload (Bypasses 8-byte UDP header context):

Target byte sequences: 0x81, 0x60, 0x03. Highly useful for diagnosing custom software implementations.

udp[8:3] == 81:60:03

Slicing for Hardware Vendor Identifiers (OUI Field Matching):

Restricts view parameters to custom hardware groups. Example for explicitly filtering targeting DELL network configurations:

eth.addr [0:3] == 00:06:5B

String Verification Using the "contains" Operator:

Looks globally for variable matches across an entire functional payload string field:

udp contains 81:60:03
sip.To contains "a1762"

Regex Engine Matches (Perl-Compatible PCRE Architecture Syntax):

Note: The application platform compilation layer must link to libpcre to run the matches operator. Example looking for string data anchor terminations ($):

http.request.uri matches "gl=se$"

Protocol Isolation While Dropping Explicit Administrative IP Ranges:

ip.src != xxx.xxx.xxx.xxx && ip.dst != xxx.xxx.xxx.xxx && sip

Critical "Gotchas" & Logical Pitfalls

Some filter operational definitions match against multiple protocol fields simultaneously. For example, ip.addr maps implicitly to both the target IP source and destination headers. Similar behaviors occur across fields like tcp.port, udp.port, and eth.addr.

The Equivalence Rules:

ip.addr == 10.43.54.65

is functionally equivalent to:

ip.src == 10.43.54.65 or ip.dst == 10.43.54.65

The Counterintuitive Inequality Bug

If trying to isolate traffic to exclude anything matching host address 10.43.54.65, you might inadvertently attempt:

ip.addr != 10.43.54.65

Because of standard logical parsing expansions, this statement actually translates to:

ip.src != 10.43.54.65 or ip.dst != 10.43.54.65

The Problem: This evaluates to passing all traffic except for frames where both source and destination simultaneously equal 10.43.54.65. This allows unwanted communications through the filter window.

The Correct Solution (Enclosing Group Negation):

! (ip.addr == 10.43.54.65)

This maps accurately to the expected statement:

! (ip.src == 10.43.54.65 or ip.dst == 10.43.54.65)

Advanced Edge Cases:

This behavior can manifest via encapsulated/tunneled protocols (resulting in multiple nested IP headers) or multi-homed IPv6 interfaces containing stacked instances of standard fields like "next header".

The Core Rule: Any expression written as name op value evaluates as "match the complete packet if there is at least one instance of this specific field matching the criteria". Negating an evaluation expression by replacing operators like == with != or < with >= simple creates another localized "at least one" conditional evaluation check, failing to cleanly invert the entire statement logic loop.
